# Dimensy patches for Frappe Helpdesk

Base: Helpdesk v1.30.1 (branch `release/1.30`). One commit per patch, written as [Conventional Commits](https://www.conventionalcommits.org/) with a `Dimensy-Patch: Pn` trailer (find them with `git log --grep "Dimensy-Patch"`). Plan: `docs/patch-plan.md` in the Dimensy project repository.

| P17 | `fix(api): strip internal ticket fields from responses to non-agents` | `helpdesk/utils.py`, `helpdesk/hooks.py` | P10/P11 vet what customers request, but endpoints that save a document answer with the whole document: `frappe.client.set_value` (used by the customer portal itself), `frappe.client.save`, REST `PUT` and `POST` returned priority, team, SLA times, channel, platform and contact details of the customer's own ticket. | P18 | `fix(ui): connect realtime on the page origin in production builds` | `desk/src/socket.ts` | The client built the socket.io URL from `socketio_port` (9000) whenever the page URL had an explicit port, and assumed https otherwise. Behind nginx, socket.io is proxied on the page's own origin, so a site opened as `http://<ip>:8000` (staging before it has a domain, and local) tried `:9000`, which is not published, and every realtime update was lost: ticket status and fields changed by the server or by others did not refresh until a reload, new tickets did not appear in the list, and viewer presence was missing. | P19 | `fix(api): let customers set several ticket fields at once` | `helpdesk/utils.py` | P11 replaced every `fieldname` that was not a string or a list with `name`, to fail closed. `frappe.client.set_value` also takes a dict of field values, and the portal sends one when a customer closes a ticket from the feedback dialog (status, feedback option and comment), so closing a ticket from the portal failed with "Cannot edit standard fields" ever since P11. A dict `fieldname` is accepted only when the method named after `/api/method/` (or `/api/v2/method/`) is exactly `frappe.client.set_value` and no other `cmd` is given, and only with scalar values that are not internal field names; it keeps its keys minus internal fields (which customers cannot write anyway) and falls back to `name` when nothing is left. Every other dict still becomes `name`: read endpoints such as `frappe.client.get_value` treat a dict as SQL functions (`{"MAX": "priority"}`), so the first version of this fix (tag r21) let customers read internal fields that way, and the second (tag r22) checked only the end of the path; neither was released. Test: `scripts/test_security.py` (Dimensy project) closes a ticket with a dict that also carries `priority` and checks that the ticket is Closed and the priority unchanged, and that `get_value` with `{"MAX": "priority"}` returns nothing, also on a path that ends in `frappe.client.set_value`. |
